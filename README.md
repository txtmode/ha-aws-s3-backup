# AWS S3 Backup for Home Assistant

Home Assistant's built-in [`aws_s3`](https://www.home-assistant.io/integrations/aws_s3)
integration, patched to accept **EC2 IAM role credentials** (via IMDS) in addition to
static access key / secret key pairs.

Dropping this into `custom_components/` overrides the built-in integration, so every
instance keeps the upstream backup agent, sensor, diagnostics and multipart upload
behaviour — it only gains a "use IAM role" option.

## Why

`oti.cat` HA instances each run on their own EC2 instance with a per-instance IAM role
scoped to a single bucket (`ha-oti-<id>`). Upstream requires static keys, which would
mean minting and storing long-lived credentials on every instance. With IMDS, nothing
is stored: botocore fetches temporary credentials from the instance metadata service.

Provisioning (`ha-init.sh`, generated by `app/api/ha/instance+api.ts` in `txtmode/web`)
clones this repo and drives the config flow over the REST API with
`{"use_iam_role": true, "bucket": …, "endpoint_url": …, "prefix": "backups"}`.

## Repository layout — vendor branch + patch

| Branch | Contents |
|--------|----------|
| `upstream` | A **pristine** copy of `homeassistant/components/aws_s3` from a tagged core release. Never edited by hand. `UPSTREAM` records the tag and sha. |
| `main` | `upstream` merged in, plus the IAM-role patch. This is what gets deployed. |

Because `upstream` is a real ancestor of `main`, updating is an ordinary three-way
merge — conflicts can only appear where core touched one of the patched lines.

### Updating to a new core release

```sh
scripts/sync-upstream.sh 2026.9.0     # vendor drop, commits on the `upstream` branch
git checkout main && git merge upstream
git push origin main upstream
```

The sync script uses a blobless sparse clone of `home-assistant/core`, so it pulls a
few MB, not the whole repo. A weekly GitHub Action
(`.github/workflows/upstream-drift.yml`) diffs core `dev` against the vendored copy and
files an issue when core moves ahead.

Every local change is tagged with a `PATCH(txtmode)` comment — `git grep 'PATCH(txtmode)'`
is the full inventory.

## The patch

| File | Change |
|------|--------|
| `const.py` | `CONF_USE_IAM_ROLE`, `DESCRIPTION_DOCS_URL` |
| `__init__.py` | Omits `aws_access_key_id` / `aws_secret_access_key` from `create_client()` in IAM-role mode so botocore resolves credentials from IMDS |
| `config_flow.py` | `use_iam_role` toggle; credential fields become optional (with a `credentials_required` check when the toggle is off); region pinned from the endpoint URL so signing never waits on an IMDS region lookup; `NoCredentialsError` / `NoRegionError` / `BotoCoreError` caught as form errors instead of escaping as a 500; credential keys never persisted in IAM-role mode; entry title suffixed `(IAM role)` |
| `strings.json` | Strings for the toggle and the `credentials_required` error |
| `manifest.json` | Fork codeowner/documentation, HACS `version`, and `aiobotocore>=2.21.1` instead of core's exact pin |

### Deliberate deviations to keep in mind on the next merge

- **`aiobotocore>=2.21.1`, not core's `==3.7.0`.** The HA AMI pre-installs aiobotocore
  in the venv; a hard pin would make every instance reinstall it (and pull a new
  botocore) at startup. Revisit when the AMI is rebuilt. Do **not** add `awscli` to the
  same venv — it conflicts with aiobotocore's botocore pin.
- **Upstream's `AWS_DOMAIN` endpoint check is kept.** All instances use
  `https://s3.<region>.amazonaws.com/`, so it never fires; non-AWS S3-compatible
  endpoints would need it relaxed.
- The region regex lives only in the config flow. `async_setup_entry` relies on
  botocore's own region resolution, which works on EC2 via IMDS.

## Installation

### HACS

1. Add `txtmode/ha-aws-s3-backup` as a custom repository.
2. Install **AWS S3 Backup**, restart Home Assistant.

### Manual

Copy `custom_components/aws_s3/` into the Home Assistant config directory.

## Configuration

**Settings → Devices & Services → Add Integration → AWS S3**

| Field | Description |
|-------|-------------|
| Use IAM role | Use the EC2 instance profile (IMDS). No credentials needed. |
| Access key ID | Required unless using an IAM role |
| Secret access key | Required unless using an IAM role |
| Bucket name | Must already exist and be accessible |
| Endpoint URL | Region-specific S3 endpoint, e.g. `https://s3.eu-south-2.amazonaws.com/` |
| Prefix | Optional folder prefix, e.g. `backups` |

## IAM role requirements

```json
{
  "Effect": "Allow",
  "Action": ["s3:GetObject", "s3:PutObject", "s3:ListBucket", "s3:DeleteObject"],
  "Resource": [
    "arn:aws:s3:::your-bucket-name",
    "arn:aws:s3:::your-bucket-name/*"
  ]
}
```
